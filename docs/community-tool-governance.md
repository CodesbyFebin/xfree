# Community tool governance

XFree accepts community-built utilities, but it does not manufacture a public
inventory from keyword combinations. Every public tool must correspond to a
distinct, working implementation whose claims can be verified against code and
tests.

## Sources of truth

- `src/data/toolsRegistry.ts` controls dedicated marketing-site tool routes.
- `src/data/publicTools.ts` exposes only `published && indexable` tools.
- `src/lib/studio/engines.ts` controls functional Studio engines.
- The content pipeline controls reviewed generated editorial artifacts.
- The sitemap consumes public, successfully rendered routes only.

Roadmap ideas, GitHub issues, draft registry entries, and Studio engines are not
indexable pages by themselves.

## Proposal requirements

A proposal must include:

1. the concrete problem it solves;
2. example inputs and expected outputs;
3. malformed-input and edge-case behavior;
4. Local, Cloud, or Hybrid processing classification;
5. network destinations and data-handling implications;
6. relevant technical specifications;
7. why the capability is distinct from existing engines.

Maintainers—not issue authors or automation—decide whether an issue is suitable
for `good first issue` or `help wanted`. The project will not bulk-create issues
from a generated matrix because issue volume is not evidence of community demand.

## Implementation gate

Contributions must preserve the React/TypeScript architecture. Raw HTML marker
files, arbitrary script injection, `innerHTML`, `eval`, and unreviewed third-party
scripts are not accepted.

The implementation review verifies:

- deterministic behavior where appropriate;
- input validation and actionable errors;
- representative and adversarial tests;
- accessible keyboard and screen-reader behavior;
- mobile usability;
- no undisclosed upload, telemetry, credential, or provider call;
- practical limits and security warnings;
- main-thread offloading for expensive operations.

Security-oriented inspection tools must not imply a stronger guarantee than they
provide. For example, decoding a JWT is not signature verification, and hashing
is not encryption.

## Publication gate

Merging a working engine does not publish an SEO page. Publication requires a
separate review covering:

- exact engine ownership and evidence;
- unique title, description, canonical, and one H1;
- truthful Local/Cloud language;
- page-specific examples, limits, and troubleshooting;
- schema generated by the application rather than editorial output;
- rendered HTML verification;
- explicit human approval bound to the exact content fingerprint.

Until that review passes, the page remains absent or `noindex`, excluded from the
sitemap, and unavailable through public discovery components.

## Roadmap presentation

The public roadmap should be a small, curated set of accepted proposals. It must
not render tens of thousands of generated names. Larger planning datasets belong
in maintainers' private planning artifacts or compact aggregate statistics backed
by real records.

Each public roadmap entry should link to one reviewed GitHub issue and state its
real status: proposed, accepted, in progress, or shipped. Shipped entries link to
the working engine and may be removed from the roadmap after release.

## Recognition

Contributors receive attribution through Git history, merged pull requests,
release notes, and an optional contributors section. Recognition must reflect
real contributions; bots must not infer contribution types or fabricate records.
